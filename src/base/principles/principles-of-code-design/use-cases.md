# UseCases или как описывать бизнес-процессы в коде

`UseCase` - это один законченный бизнес-сценарий системы или сценарий использования

Это нам дает то что `use case` обрабатывает только бизнес логику, позволяет легко тестировать, так как `use case` не зависит от `http` запросов.

Вся логика в одном месте, нет хауса в коде. `use case` можно переиспользовать из разных мест.

## Примеры

- зарегистрировать пользователя
- создать заказ
- авторизовать пользователя
- изменить статус заявки
- сформировать счёт
- публикация поста в блоге

::: tip
Важно тут понимать, процесс это не записать в базу данных, а именно "Пользователь оформляет заказ".
:::

`Use Case` вводит понятную структуру: система описывается через явные бизнес-сценарии, а не через абстрактные сущности вроде `Service`, `Manager` или `Helper`.

## Ограничения

Не рекомендуется вызывать один `use case` из другого.

Если есть такая необходимость рекомендуется вынести в отдельные сервисы или доменные компоненты и их использовать в разных `use cases`.

## Откуда можно вызвать

- Контроллер
- Консольная команда
- Событие
- Очередь

::: tip
`Use Case` это ручки, через которые внешний мир взаимодействует с бизнес-логикой приложения.
:::


## Какие проблемы могли возникнуть

По началу когда проект маленький все в одном классе выглядит здравым решением, но с ростом проекта появляются дополнительные шаги.

- проверить остатки
- применить скидку
- списать баланс
- отправить уведомление
- записать аналитику 

В результате в одном классе у нас:

- много зависимостей
- много методов
- много побочных эффектов
- сложно читать код
- сложно писать тесты 

Важно помнить, что проблема не в самом классе, а в отсутствии явных границ сценариев. 

Без разделения на `UseCase` любая реализация со временем начинает разрастаться и усложняться.

::: tip
один `Use Case` один бизнес процесс.
:::

## Структура

Можно по разному писать `use case`.

Обычно это три части:

- Handler
- DataInput
- DataOutput

`Handler` начинает выполнять оркестрацию - он управляет последовательностью шагов сценария.

`use cases` должны управлять последовательностью выполнения сценария, могут содержать условия выполнения шагов. Не должны содержать доменную бизнес логику.

Все расчеты должны быть вынесены отдельно.

То есть если это создание заказа, значит должна быть функциональность создания заказа. 

Глядя на директорию должно быть сразу понятно что происходит, например

- app/UseCases/StoreOder- создание заказа
- app/UseCases/CancelOrder- отмена заказа
- app/UseCases/RegisterUser - регистрация пользователя
- app/UseCases/AuthorizeUser- авторизация пользователя

Важно тут что умеет делать система, а не как она это делает.
