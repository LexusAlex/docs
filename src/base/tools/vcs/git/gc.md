# git gc

**Уровень:** Продвинутый
**Минимальная версия Git:** 0.99

`git gc` обслуживает локальный репозиторий: упаковывает объекты, удаляет устаревшие служебные данные и оптимизирует внутренние структуры. В обычной работе Git запускает обслуживание автоматически, поэтому ручной `gc` требуется редко.

## Синтаксис

```bash
git gc [<options>]
```

## Основные опции

| Опция | Описание |
|---|---|
| `--auto` | Запустить обслуживание, только если достигнуты настроенные пороги |
| `--aggressive` | Потратить заметно больше времени на повторное сжатие |
| `--prune=<date>` | Удалить недостижимые loose-объекты старше указанной даты |
| `--no-prune` | Не удалять loose-объекты |
| `--cruft` / `--no-cruft` | Включить или отключить упаковку недостижимых объектов в cruft pack |
| `--max-cruft-size=<n>` | Ограничить размер новых cruft pack |
| `--expire-to=<dir>` | Сохранить удаляемые cruft-объекты во внешнем каталоге |
| `--keep-largest-pack` | Не переупаковывать самый большой pack-файл |
| `--force` | Запустить `gc`, даже если другой процесс `gc` уже обнаружен |
| `--quiet` | Сократить вывод |

Опций `--depth`, `--window`, `--max-pack-size` и `--verbose` у `git gc` нет. Параметры упаковки настраиваются через `git repack` и конфигурацию, а диагностика — отдельными командами.

## Обычное обслуживание

```bash
git gc --auto
```

Git также может запускать эту проверку из команд, создающих объекты. Для больших активных репозиториев удобнее фоновое обслуживание:

```bash
git maintenance start
```

Команда регистрирует периодические задачи поддерживаемым для платформы способом. Проверить конфигурацию:

```bash
git maintenance run --auto
git config --get-regexp '^maintenance\.'
```

## Ручная оптимизация после крупного импорта

```bash
git status --short
git gc
git count-objects -vH
```

Запускайте ручной `gc`, когда репозиторий не изменяется другими процессами. Не прерывайте операцию без необходимости.

### Когда уместен `--aggressive`

```bash
git gc --aggressive
```

Это дорогая повторная оптимизация. Она может помочь после большого одноразового импорта, но обычно даёт небольшую выгоду и не нужна по расписанию. Сначала измерьте размер и скорость обычного `git gc`.

## Срок хранения и восстановление

По умолчанию обычные записи reflog хранятся примерно 90 дней, а недостижимые — примерно 30 дней. Реальные сроки зависят от конфигурации:

```bash
git config --get gc.reflogExpire
git config --get gc.reflogExpireUnreachable
git config --get gc.pruneExpire
```

::: danger Не используйте `--prune=now` как обычную очистку
`git gc --prune=now` удаляет недостижимые loose-объекты без стандартного периода ожидания. Это сокращает окно восстановления и может конфликтовать с параллельной записью объектов. Перед обслуживанием остановите процессы, создающие объекты, и сделайте резервную копию важного репозитория.
:::

Если данные нужно восстановить, сначала ничего не удаляйте:

```bash
git reflog --all --date=local
git fsck --no-reflogs --unreachable
```

Найдя нужный коммит, закрепите его веткой:

```bash
git branch recovered-work <commit>
```

После `prune=now` или ручного удаления объектов восстановление может стать невозможным.

## Диагностика размера

```bash
git count-objects -vH
git verify-pack -v .git/objects/pack/*.idx
```

Вторая команда может вывести очень много данных; применяйте её только для анализа pack-файлов. Для проверки целостности используйте:

```bash
git fsck --full
```
