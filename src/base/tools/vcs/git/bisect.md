# git bisect

**Уровень:** Продвинутый
**Минимальная версия Git:** 1.5

`git bisect` бинарным поиском находит коммит, в котором изменилось проверяемое поведение. Вместо просмотра каждого коммита потребуется примерно `log2(N)` проверок.

## Ручной поиск

```bash
git bisect start
git bisect bad              # текущий коммит содержит проблему
git bisect good v2.3.0      # эта версия точно работала
```

Git checkout-ит промежуточный коммит. Выполните одну и ту же проверку и отметьте результат:

```bash
git bisect good
# или
git bisect bad
```

Повторяйте, пока Git не покажет первый bad commit. Завершите и вернитесь к исходной ветке:

```bash
git bisect reset
```

Не передавайте `HEAD`, если хотите вернуться в состояние до `bisect`: к концу поиска `HEAD` указывает на тестируемый коммит.

## Короткий старт

Если известны обе границы:

```bash
git bisect start HEAD v2.3.0
```

Первый аргумент — bad, второй — good.

## Автоматический поиск

```bash
git bisect start HEAD v2.3.0
git bisect run ./test-regression.sh
```

Скрипт должен возвращать:

| Код | Значение |
|---:|---|
| `0` | good |
| `1`–`124` | bad |
| `125` | skip: коммит невозможно проверить |
| `126`–`127` | ошибка запуска команды, bisect прерывается |
| `128` и выше | фатальная ошибка, bisect прерывается |

Пример shell-скрипта:

```bash
#!/usr/bin/env bash
set -o pipefail
npm test -- --runInBand tests/login.test.js
```

После результата:

```bash
git show --stat
git bisect log
git bisect reset
```

## Пропустить непроверяемый коммит

```bash
git bisect skip
```

Несколько известных коммитов или диапазон:

```bash
git bisect skip <commit1> <commit2>
git bisect skip <oldest>..<newest>
```

Если пропусков много рядом с границей, Git может выдать несколько возможных первых bad-коммитов вместо одного.

## Пользовательские термины

Если «good/bad» неудобны, можно выбрать, например, `old/new`:

```bash
git bisect start --term-old=fast --term-new=slow
git bisect slow HEAD
git bisect fast v2.3.0
```

После этого отмечайте коммиты `git bisect fast` и `git bisect slow`.

## Проверить только определённый путь

```bash
git bisect start HEAD v2.3.0 -- src/auth/
```

Git учитывает только коммиты, меняющие pathspec. Используйте это, только если уверены, что причина находится в данном пути.

## Воспроизвести результат

```bash
git bisect log > bisect.log
git bisect reset
git bisect replay bisect.log
```

Лог позволяет повторить решения и проверить поиск.

## Практические советы

- Сначала сформулируйте детерминированный тест.
- Убедитесь, что good-граница действительно проходит, а bad — падает.
- Не исправляйте код прямо во время ручного bisect; это загрязняет следующие проверки.
- Для коммитов с несовместимой сборкой возвращайте `125`, а не помечайте их bad.
- После найденного коммита проверьте его патч: корреляция не всегда означает истинную причину.
