# git blame

**Уровень:** Средний
**Минимальная версия Git:** 1.5

`git blame` показывает, какой коммит последним изменил каждую строку файла; переименования целого файла отслеживаются автоматически. Это отправная точка для понимания контекста, а не надёжный способ назначить «виновного»: форматирование и перенос кода могут скрыть настоящего автора идеи.

## Синтаксис

```bash
git blame [<options>] [<rev>] -- <file>
```

## Основные опции

| Опция | Описание |
|---|---|
| `-L <start>,<end>` | Ограничить диапазон строк |
| `-L :<funcname>` | Показать функцию по шаблону из userdiff |
| `-w` | Игнорировать изменения пробелов |
| `-M[<n>]` | Находить перемещённые строки внутри файла |
| `-C[<n>]` | Находить строки, скопированные/перемещённые из других файлов |
| `--reverse <start>..<end>` | Показать последний коммит, в котором строка ещё существовала |
| `--ignore-rev <rev>` | Игнорировать выбранный массовый рефакторинг |
| `--ignore-revs-file <file>` | Прочитать игнорируемые commits из файла |
| `--line-porcelain` | Стабильный подробный формат для машинной обработки |
| `-e` | Показывать email автора |
| `-s` | Скрыть имя автора и timestamp |

У `git blame` нет произвольной опции `--format="..."`. Для скриптов используйте `--line-porcelain`.

## Базовые примеры

```bash
git blame -- src/app.js
git blame -L 40,60 -- src/app.js
git blame -L :handleLogin -- src/app.js
```

Показать состояние на старом коммите:

```bash
git blame v2.4.0 -- src/app.js
```

## Игнорировать форматирование

```bash
git blame -w -- src/app.js
```

Для известного массового форматирующего коммита:

```bash
git blame --ignore-rev <formatting-commit> -- src/app.js
```

Команда проекта может хранить список таких коммитов, например `.git-blame-ignore-revs`:

```bash
git blame --ignore-revs-file .git-blame-ignore-revs -- src/app.js
```

Настройка по умолчанию для репозитория:

```bash
git config blame.ignoreRevsFile .git-blame-ignore-revs
```

## Найти перенос кода

```bash
git blame -M -C -- src/app.js
```

Один `-C` ищет копии из файлов того же коммита; повторение расширяет поиск, но делает его дороже:

```bash
git blame -M -C -C -- src/app.js
```

## Перейти к коммиту строки

Сначала получите хеш визуально:

```bash
git blame -L 42,42 -- src/app.js
git show <commit> -- src/app.js
```

Такой двухшаговый пример переносим между оболочками и позволяет проверить хеш, в отличие от хрупких `awk | xargs` конвейеров.

## Машинный разбор

```bash
git blame --line-porcelain -- src/app.js
```

Porcelain-вывод повторяет метаданные для каждой строки и предназначен для программ. Не разбирайте обычный выровненный вывод: его формат может меняться из-за настроек и ширины хеша.

## Обратный blame

```bash
git blame --reverse v2.3.0..main -- src/app.js
```

Показывает последний коммит диапазона, в котором существовали строки из начальной версии. Начальная точка обязательна.

## Ограничения

- Blame показывает последний изменивший строку коммит, а не автора всей логики.
- Сгенерированные файлы и vendor-код лучше исключать из анализа.
- Большие reformat-коммиты снижают полезность результата; используйте ignore-revs.
- В shallow clone нужной истории может не быть.

`git annotate` — совместимый синоним с небольшими отличиями формата, но для новых инструкций используйте `git blame`.
