59. Materialized Path для хранения иерахических данных Идея в Materialized path заключается в том, что каждый узел (каждая запись в базе) хранит полный путь до корня. То есть вместо parent_id, мы добавляем path, который выглядит, например, так: 1/2/5/8/99/3. / - часто используется как разделитель, но можно выбрать и другой. 1 - в примере это корень под который попадает текущая запись, 3 это прямой родитель. Все что между это промежуточные родительские записи.  Этим подходом мы сразу решили проблему выборку всей нужной ветки. Все что нам надо будет сделать это в коде разделить 1/2/5/8/99/3 на идентификаторы, и сделать один in запрос IN (1, 2, 5, 8, 99, 3) SELECT * FROM <name> WHERE path LIKE '1/2/%';

Советы:
1. Всегда храним исторические данные, чтобы понять как оно было и как стало
2. Валидация проверяет только формат данных, остальное уже не валидация https://github.com/yiisoft/validator http://yugeon-dev.blogspot.com/2010/09/blog-post.html
3. Пишем код устойчивый к работе в трех окружениях
4. Проект - это набор контекстов, удобный подход с разбитием на модули
5. Всегда анализировать предметную область, понять какие подсистемы будут в проекте
6. Команды модифицируют модуль - POST, запросы считывают из модуля - GET
7. Идентификация - Аутентификация - Авторизация(наделение пользователя правами)
8. При проектировании модуля определяем какие сущности будут в системе, исходя из контекста модуля
   1. При проектировании фронтенда можно использовать следующие слои
    - app - это все приложение
    - entities - бизнес сущности
    - kernel - ядро связи всего
    - shared - инфраструктурные вещи
    - features - бизнес функционал
9. По максимому используем чистые технологии html css js, в идеале, так лучше понимаешь что происходит. Для этого можем использовать vite
10. Пакеты берем обособленные по аналогии как backend-php
